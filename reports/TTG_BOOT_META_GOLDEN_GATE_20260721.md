## Sanitized Observed-Product Sequence

The observed external product opened the Preloader COM port at `921600`, even
parity, 8 data bits, and 1 stop bit. A metadata-only serial trace recorded this
control sequence without retaining opaque payload bytes:

```text
serial line setup and purge
  -> METAMETA
  -> 12-byte control acknowledgement
  -> serial line reset and purge
  -> SLASTART + NUL
  -> opaque 16-byte control frame
  -> 12-byte control acknowledgement
  -> opaque 16-byte control frame
  -> DISCONNECT
  -> PID_2007 approximately 13 seconds later
```

No 256-byte response was observed. Earlier assumptions that this target uses a
static 256-byte RSA response are therefore rejected.

## MetaCore Boundary

Static ABI and control-flow review found:

- `_Boot_META@16` is a compatibility stub that immediately returns status
  `0x410`; it is not the working entry point.
- `_Preloader_BootMode@4` rejects a null single argument with status `0x3EA`.
- Its non-null path treats that argument as a boot-context structure, starts the
  boot-mode entry procedure, and enters the internal Preloader state machine.
- MetaCore's own `DumpBootArg` diagnostics enumerate an SLA challenge callback,
  callback argument, challenge-end callback, and authentication/certificate
  handles.
- The internal `CMD_BootAsMETA` state machine owns the 12-byte and 16-byte host
  writes around `SLASTART`; they are not generated by the USB watcher.

The remaining gap is therefore a correctly initialized, callback-driven boot
context. Guessing `_SPMeta_ConnectWithPreloader@8` arguments, replaying opaque
frames, or extending the enumeration timeout cannot resolve that boundary.

## Privacy Boundary

The evidence excludes IMEI, serial number, fingerprint, full Windows device-instance IDs, NVRAM/NVDATA contents, credentials, tokens, cookies, activation material, and customer data. The golden gate reads only META state, platform/build metadata, and chipset identity.
